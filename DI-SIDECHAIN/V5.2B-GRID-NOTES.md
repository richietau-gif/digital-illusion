# DI SIDECHAIN 5.2B — GRID sequencer prototype

Development branch: `feature/di-sidechain-v5.2b-grid` (based on `di-sidechain-5.1-dev`).

## Implemented in the first iteration
- Replace the sequencer's single-lane envelope overview with a three-row, sixteen-column grid.
- Show VOLUME, FILTER and PAN simultaneously, with independent lane colours and per-cell curve-derived intensity.
- Highlight the current transport step (green) and the selected lane/step (orange).
- Click any cell to select its lane and step without inadvertently modifying the stored automation.
- Keep the existing detail curve editor, 16-step DSP/state model, A/B snapshots, presets and filter/FX controls.
- Identify the experimental GUI as version 5.2B.

## Scope and limitations
This is an original layout inspired by the interaction model visible in the supplied omniGRID reference, not a copy of omniGRID artwork or source code. The current processing engine has three modulation lanes, not omniGRID's arbitrary tracks, pads and MIDI clip engine. Each grid cell represents a sidechain modulation curve, not a MIDI note. The active step is derived from the existing DSP transport.

## Validation required before merge

- Check 50%, 75%, 100% UI scale, clicking all 16 steps and all 3 lanes.
- Verify sequence step-count reductions (1–16), project transport and tempo sync, MIDI/audio triggers.

## Follow-up from six omniGRID screenshots (2026-11-09)

**Important correction:** omniGRID's Track 1/2/3 rows are independent notes or trigger streams belonging to the *same* instrument. They are not equivalent to DI SIDECHAIN's Volume/Filter/Pan modulation lanes. The first 5.2B UI prototype still shows these modulation lanes; that is an intermediate interface only and should not be described as the final intended track model.

### Implemented foundation
`Source/DuckTrackGrid.h` is a standalone fixed-size data model for 8 independent duck-trigger tracks x 16 steps x 4 scenes. Each cell has enable, velocity/depth, length and signed timing shift. Each track has mute; scenes can be copied. Shared step-position evaluation produces a bitmask of simultaneous triggers. This header is deliberately NOT connected to audio processing, GUI, automation or plugin serialization yet. A standalone smoke test is registered in CMake.

### Desired 5.2B UX
- Left: TRACK 1 ... TRACK 8 (optional human labels KICK/SNARE/GHOST/etc.), track mute, select and add/remove in a later iteration.
- Center: 16-step grid with inactive charcoal cells, lime active blocks, selected amber border and green transport position marker. A block represents an active duck trigger, **not** a continuously filled curve average.
- Below: edit selected track/cell envelope with velocity/depth, duration, shift/offset and shape; preserve existing advanced filter controls always visible.
- Optional SCENE A/B/C/D pattern selection and copy, inspired by the screenshot's scene menu.
- Retain legacy Volume/Filter/Pan modulation as effects routing/settings, rather than treating them as parallel trigger tracks.
- Preserve Ableton song position, BPM/beat division, external audio/MIDI triggering, preset/state compatibility and low-latency realtime processing.
- At simultaneous trigger events, define an explicit safe overlap algorithm (e.g. strongest duck wins; do not blindly multiply envelopes) and ensure deterministic playback after seeking and loop wraps.

### Next engineering milestones
1. Wire the new data model to processor state with backward-compatible defaults, preset save/restore and GUI access; use race-free data transfer to audio thread.
2. Replace preliminary 3-lane graph with true eight-track event grid and implement click/toggle and block editing, plus scene controls.
3. Schedule individual duck envelopes against sample-accurate Ableton song position and define MIDI/audio trigger routing and overlap semantics.
